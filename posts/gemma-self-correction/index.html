Gemma 1B won’t fix its own code

Given a failing test and the exact error, Google’s smallest Gemma sends back the same code. Asking it to start over works far better than asking it to fix.

Part of Teaching Gemma 1B, a series of small post-training experiments on one 1B model.

Gemma 3 1B can write code: it solved 88% of simple write-a-function problems on the first try. But when its code failed a test and I told it exactly what went wrong, it resubmitted the identical code 95% of the time and fixed only 1% of its failures.

Its explanation contradicts itself: it agrees the test fails, then says the code produces exactly the expected output. It can’t check its code against the feedback, so it repeats the code and explains why it’s right.

Starting over beats fixing

On the 20 problems where its first attempt failed, the model writes correct code from scratch about a third of the time. Shown its failed attempt and the test feedback, it fixes it 1% of the time. Seeing its own wrong answer makes it far worse than starting over, because it copies it.

It isn’t loyalty to its own answer. I showed it the same wrong code as a colleague’s, in the user’s message instead of its own previous turn, and it fixed 0.8% (versus 0.9%). What matters is the kind of bug. A one-character slip in otherwise correct code gets fixed as often as writing from scratch, while the model’s own mistakes are what it actually believes is the answer, so it writes them again.

It also can’t run even simple code in its head to check. Asked “In Python, what does 'hi' * 3 evaluate to?”, it answered 'hihihi' only 11 times out of 32; most other answers were 'hihi' or 'hi'. The feedback tells it the code is wrong, and it has no way to see why.

Fine-tuning breaks the habit, mostly

I fine-tuned it on 652 conversations where the 1B model made an attempt, it failed, and a model about four times larger (Gemma 4 E4B) continued from the test feedback until the tests passed. The 1B model was trained only on the larger model’s turns, never on its own wrong attempt.

So the habit of repeating itself went away almost completely, but the skill of actually fixing the bug barely arrived, and because first tries got worse, overall success hardly moved. A short reinforcement learning run on top made recovery worse, not better (7% → 3%).

What I took away

  • For a small model, acting on feedback is the bottleneck, not writing code.
  • When a small model is wrong, ask again instead of asking it to fix. On the same problems a fresh answer was correct 34% of the time; a retry with feedback, 1%.
  • Its mistakes aren’t slips. It fixes a one-character typo as readily as it writes the code fresh, but it writes its own mistakes again, whoever it’s told wrote them.
  • Fine-tuning changes behaviour quickly, including the behaviour you didn’t want. 652 examples stopped the repetition, and also tripled the reply length.

All sampling at temperature 1.0. Up to four tries per problem, with hidden tests so hard-coding the visible answers doesn’t count.
