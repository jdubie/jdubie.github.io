Teaching Gemma 1B Countdown with reinforcement learning

No demonstrations, no teacher model: just puzzles, a checker, and 300 steps of reinforcement learning on one GPU.

Part of Teaching Gemma 1B, a series of small post-training experiments on one 1B model.

Base Gemma 3 1B solved 5% of new Countdown puzzles. After two hours of reinforcement learning, it solves 58%. The model never saw a worked solution. It only learned which of its own attempts the checker accepted.

The game

Each puzzle gives three numbers and a target: “Using 6, 10 and 17, each exactly once, and +, −, ×, ÷, make 112.” The answer is an expression, and checking it takes a few lines of Python: it must use each number exactly once, contain only arithmetic, and equal the target. Puzzles are generated at random, so there is an endless supply and no answer key to memorise.

Base Gemma is bad at this. It writes expressions that don't equal the target, uses numbers twice, or invents new ones, then declares success: “6 + 10 × 17 − 1 = 112”.

Why this task suits RL

Reinforcement learning can only reinforce successes the model already produces sometimes. Before training I measured that directly: given eight tries, base Gemma solved 19% of puzzles at least once, but only 5% on a single try. That gap is the room RL has to work with. It doesn't need to teach the model anything new, only to make its occasional successes reliable.

I measured five candidate tasks this way. Countdown had the biggest gap between best-of-eight and single-try, so it got the RL run.

Setup

  • Algorithm: GRPO-style policy gradient. Each step draws 32 fresh puzzles and samples 8 answers to each. The reward is 1 if the checker accepts the answer and 0 otherwise. Each answer's advantage is its reward minus the average for its puzzle, so the model is pushed toward the answers that beat their siblings.
  • Model: Gemma 3 1B instruct with a LoRA adapter (rank 32, all linear layers), learning rate 2e-5, loss averaged per answer. A single L4 GPU does both the sampling (vLLM, with the new adapter hot-loaded after every step) and the training.
  • Scale: 300 steps, 76,800 sampled answers, about two hours.
  • Measurement: a fixed set of dev puzzles scored every 20 steps, and a separate set of new test puzzles for the final numbers. Training puzzles are drawn fresh at every step.

Results

On new test puzzles, single-try accuracy went from 5% (95% interval 3%–7%) to 58% (52%–64%). Best-of-8 went from 19% to 66%.

What RL taught it

The base model writes one expression and declares victory, whether or not it's right. After RL the model searches: it writes a candidate, works it out, says “This is not 25”, tries another, and answers only when the arithmetic checks out. Nobody showed it that procedure. Answers that happened to check their work were rewarded more often, so checking became the habit.

Its remaining failures are mostly searches that loop over the same few candidates until they hit the 384-token reply limit.

And then it collapsed

The run did not end well. I paused training at step 320 to free the GPU for another experiment, then resumed from the saved adapter with a fresh optimizer. Within 50 steps the gradient norm spiked from about 1 to 15, and by step 370 the model never solved a puzzle again. With every answer scoring 0, there is no difference between good and bad samples, so no gradient to recover with. The dev curve above shows the cliff. The checkpoints kept every 20 steps made this harmless: the result below uses the step-300 checkpoint, picked by dev-set score before looking at the test set. Next time I'd save the optimizer state with the adapter, and add a KL penalty or lower the learning rate late in training.

Puzzle: Using 8, 7, 6, make 5.

Base
Here's the solution:

8 - 7 * 6 + 9 = 5

Answer: 8 - 7 * 6 + 9
After RL
8 + 7 + 6 = 21, which is not 5. 8 - 7 + 6 = 1 + 6 = 7, which is not 5. 8 * 7 - 6 = 56 - 6 = 50, which is not 5. 8 * 6 + 7 = 48 + 7 = 55, which is not 5. 8 + 7 - 6 = 15 - 6 = 9, which is not 5. 7 - 8 + 6 = 7 - 8 + 6 = -1 + 6 = 5.

Answer: 7 - 8 + 6.

What I took away

  • Measure best-of-k before running RL. RL turns occasional successes into reliable ones. A task where the base model never succeeds gives it nothing to work with; a task with a wide gap between best-of-8 and single-try is where it pays off.
  • Checkable tasks make RL cheap. No labels and no teacher: a random puzzle generator and a ten-line checker were the whole dataset.
  • Normalise the loss per answer. In an earlier, failed run on a harder coding task, summing the loss over tokens let long failed answers dominate the update and the model degraded. Averaging per answer kept this run stable for its first 300 steps; the later collapse came after a restart that reset the optimizer.

Sampling at temperature 1.0 throughout. Dev and test puzzles come from separate random seeds and never appear in training.
