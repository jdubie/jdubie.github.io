Gemma 1B can write code. It can't take feedback.

I tried to turn Google's smallest Gemma into a coding agent. Writing code turned out to be the easy part; the hard part was getting it to act on a failing test. Fine-tuning on a bigger Gemma's fixes, then reinforcement learning, is how I tried to teach it.

Part of Teaching Gemma 1B, a series of small post-training experiments on one 1B model.

Told exactly which test failed and why, Gemma 3 1B resubmitted the same code 95% of the time and fixed only 1% of its failures. Fine-tuning on a larger Gemma's fixes cut identical resubmissions to 5% and raised recovery several-fold on every eval, but the model also got wordier and worse on the first try, so overall success barely moved. A short RL run on top made it worse: final success on the feedback-only eval fell from 13% to 9%. Writing code was the easy part for a 1B model; acting on feedback was the hard part.

The model writes code. It doesn't revise it.

I started where most coding-agent work starts: small Python projects with a bug, a test suite, and tools to read files, edit them and run the tests. Gemma 3 1B scored 0%. Even when I told it the exact line the bug was on, it wrote the correct fix only about 6% of the time. Usually it copied the buggy line back unchanged.

Two things moved the number. First, the tool format: my own command syntax got 0%, and Gemma's native ```tool_code function-call format got 10% on the same tasks. Second, and more important, what I asked it to do. Asked to write a function from a clear description and a few tests, it got 88% of a 120-problem set right on the first try. It can code.

What it can't do is revise. When a test fails and the harness says exactly what went wrong (repeat_word('hi', 3) returned 'hihihi', but expected 'hi hi hi'), it sends back the same code, character for character. Shown someone else's buggy code with the same feedback, it fixes it 60% of the time. Shown its own failed attempt, 1%: it resubmits the identical code 96% of the time.

Three evals built around feedback

Every eval uses the same loop: the model writes code, the harness runs the visible tests, failures come back in plain English, and the model gets up to four tries. Grading uses hidden tests as well, so hard-coding the visible answers doesn't count. I track three numbers: success on the first try, success after all tries, and recovery, the share of first-try failures that the feedback rescues.

  • Spec discovery (80 hand-written problems). The description is deliberately vague (“formats a price given in cents”). The exact requirement, '$12.50', only appears in the failing-test feedback. It measures one thing: does the model use what the environment tells it?
  • Modules (300 tasks). Three, five or eight functions per task. Getting most of them right is easy; finding and fixing the one that's wrong, without breaking the others, is the agentic part.
  • HumanEval+ and MBPP+ (540 problems). Standard benchmarks with EvalPlus's extra hidden tests, as an outside check. I never tuned anything on them.

Training

  1. Data. MBPP problems that are not in MBPP+ (583 functions), in three styles: tests shown, tests hidden, and multi-function modules.
  2. SFT. The 1B student makes the first attempt. When it fails, Gemma 4 E4B (about four times larger) continues the same conversation from the test feedback until the tests pass. The student is trained only on the teacher's turns, never on its own wrong attempt. I also kept the student's own correct first tries and some teacher solutions written from scratch. The SFT set was 652 conversations from 341 training problems: 361 teacher fixes after a failed student attempt, 176 of the student's own correct first tries, and 115 teacher solutions. LoRA rank 64 on every linear layer, two epochs, about twenty minutes.
  3. RL. Multi-turn GRPO: eight full episodes per problem, reward 1 if the final code passes every test (hidden ones included), advantage = reward minus the group's mean. LoRA adapters, hot-loaded into vLLM after each step, so sampling and training share one L4 GPU. Each step used 16 problems × 8 episodes, up to four attempts each. Run 1 summed the loss over tokens at learning rate 2e-5 and became unstable after about ten steps (gradient norm 0.1 → 0.45, falling reward). I restarted from the step-10 adapter with the loss averaged per episode and learning rate 1e-5, which stayed stable. The final model has 19 steps in total, about 2,400 episodes; each step took five to seven minutes on the shared GPU, so this is a short run.

Results

SFT taught the model to revise. On retries, the base model resubmitted identical code 95% of the time; after SFT, 5%. Recovery rose on every eval, including HumanEval+ and MBPP+, which it never trained on: Spec discovery 1% → 7%, Modules, 3 functions 2% → 7%, HumanEval+ 0% → 3%, MBPP+ 1% → 7%.

But it cost first-try accuracy, so final success barely moved. On spec discovery final success went from 11% to 13%; on 3-function modules it fell from 40% to 35%. The student copied the teacher's style along with its fixes: its median reply is 1,607 characters, against 466 for the base model and 680 for the teacher. On 8-function modules a fifth of its answers ran past the 1,024-token reply limit before the code block closed.

RL (19 steps) — final success, SFT → SFT + RL: Spec discovery 13% → 9%; Modules, 3 functions 35% → 26%; HumanEval+ 32% → 29%; MBPP+ 53% → 45%. RL lowered final success and recovery (spec discovery recovery 7% → 3%; best of 8 38% → 25%). The checkpoint after the first ten steps already had lower recovery (3.4% on spec discovery, 4 samples per problem), so the damage started during the unstable first run and continued after I fixed the normalisation. RL also made replies longer still (median 2,322 characters, against 1,607 after SFT), so more answers ran out of tokens: on 8-function modules a third of them had no complete code block.

What I took away

  • For small models, acting on feedback is the bottleneck, not writing code. The base model solved most write-from-spec problems on the first try but almost never used a failing test to fix anything.
  • Models defend their own previous turn. The same model fixed someone else's buggy code 60% of the time and its own 1% of the time.
  • SFT moves behaviour fast, and copies style just as fast. 652 examples were enough to stop the model repeating itself and to raise recovery 4–10×, on benchmarks it never saw. They were also enough to make it three times wordier, which cost first-try accuracy. Next time I would shorten the teacher's explanations before training, or train on its code only.
  • Normalise RL loss per episode in multi-turn settings. My first RL run summed the loss over tokens. Failed episodes use every attempt and so have about four times as many tokens, so the “push failures down” term dominated: the gradient norm quadrupled and reward fell. Averaging per episode, as the original GRPO does, fixed the instability.
  • A short RL run is not a free win. Nineteen steps (about 2,400 episodes) lowered every metric, on HumanEval+ and MBPP+ as well. Only about a third of problem groups had mixed outcomes and so gave any learning signal; the first half of the run was unstable; and the training problems (MBPP, mostly with tests shown) differ from spec discovery. With more time I would filter training problems to ones the SFT model sometimes solves, use per-episode normalisation and a lower learning rate from the start, add a KL penalty toward the SFT model, and watch a fixed validation set during training instead of the noisy per-batch reward.
  • Match the model's trained tool format, and measure the base model before designing the task. My first three benchmarks scored 0% for reasons that had nothing to do with coding.

Caveats

  • The evals are small (80 to 540 problems). The table shows 95% bootstrap intervals over problems; differences inside them are noise.
  • All sampling is at temperature 1.0, Gemma's default. The teacher ran in FP8 so that both models fit on one GPU.
  • Everything ran on a single 24 GB L4 (about ten hours on one Spot L4 VM, for evals, data generation, SFT and RL together), so the SFT dataset and the RL run were cut to fit in one night.
