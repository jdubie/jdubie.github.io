pgwire-db: a PostgreSQL 16 server, wire protocol and all, where every persisted file is empty

The benchmark is built and calibrated, and two 20-minute smoke runs leave plenty of headroom. Real PostgreSQL 16 scores 1.000 on all five components (storage rule off); a server that stores data in file contents scores 0 (82 storage violations); v1's 250-line toy scores 0.032; v1's Haiku server (0.703 on v1) scores 0.215. In 20 minutes each, Opus 5.5 scored 0.429 and Haiku 5.5 scored 0.143, both with no storage violations. Neither earned any scale credit: Opus's server could not load pgbench -i -s 10 within 10 minutes.

Smoke runs (20 minutes each)

Opus 5.5: 0.429

No storage violations. Protocol 0.529 (36/68), clients 0.443 (psql 3/8, psycopg 13/29, node 9/12, JDBC 9/14, pgbench 0/6), sql 0.149 (4,507/26,127 statements), acid 0.849 (37/42 scenario runs, 103/126 crash points), scale 0 (pgbench -i -s 10 hit the 10-minute limit).

One 2,600-line Python file. Storage is a write-ahead log in names: each commit creates a directory of empty files whose names encode the operations (long rows split into chunked names), renames it from x<id> to c<id> as the atomic commit point, then applies it to per-table directories of one-name-per-row files and removes the log. Protocol: trust, MD5, cleartext and SCRAM-SHA-256 auth (all pass) and the extended protocol. It also has code for binary parameters and results, COPY text/csv/binary, CancelRequest and LISTEN/NOTIFY, but every conformance test of those differs from PostgreSQL somewhere. It missed FOR UPDATE NOWAIT / SKIP LOCKED, deadlock detection, and anything pgbench needs at speed.

It worked in a single 17-minute session: it ran the whole public suite once, then only protocol and ACID checks while fixing. It spent the last 2 minutes in 13 short resumes declining to change anything ("no time to change and re-test anything safely"). It stopped early, like Haiku, but at minute 17 rather than 14.

Haiku 5.5: 0.143

No storage violations. Scores: protocol 0.147 (10/68), clients 0.110 (psql 1/8, psycopg 5/29, node 3/12, pgbench 0/6, JDBC 0/14), sql 0.101 (3,120/26,127 statements), acid 0.266 (19/42 scenario runs, 10/106 crash points), scale 0.

Haiku 5.5 wrote one 1,450-line Python file: a hand-rolled tokenizer and parser for CREATE TABLE, INSERT, SELECT with WHERE/ORDER BY and a few aggregates, UPDATE, DELETE, CREATE TABLE AS, COPY FROM STDIN, the extended protocol with text parameters, MD5 and cleartext auth (not SCRAM). Storage is one directory per table and one empty file per row, the row JSON base64-encoded in the file name; everything is loaded into memory at start. Commits write each changed row as its own file, so a kill inside a multi-row commit leaves a partial state: it failed 96 of 106 commit-window crash points, though the timed SIGKILL scenarios mostly passed.

It worked for about 14 of the 20 minutes. From the third session on it repeatedly said it was "near the end of the window" and stopped early, and from minute 14 it answered every resume nudge with "holding at the current state": 149 CLI sessions, 134 of them one-turn no-ops. It never ran the public scale check, and first ran the public SQL subset at minute 9. It passed a group name to run_public.py clients, which the runner ignored, so each check ran all five clients (fixed in the kit since).

Its workspace was copied before two grader changes made during the run: the 3-timeout SQL abort (its PROMPT.md does not mention it) and the crash-point control fix. It was graded after both; before the crash-point fix its reward read 0.163.

What is graded

Every answer is compared with real PostgreSQL 16.16 answering the same thing, recorded twice on fresh servers; anything the two recordings disagree on is dropped. Clients are pinned in the grader image (psql/pgbench 16.16, psycopg 3.2.3, node-postgres 8.13.1, pgJDBC 42.7.4); there is no network at grade time. The full statement of the task is task/PROMPT.md.

acid0.25Half: 21 crash and isolation scenarios, 42 seeded runs (SIGKILL mid-transaction and during COMMIT, 4 concurrent writers on simple and extended protocol, pgbench TPC-B killed mid-run, READ COMMITTED, REPEATABLE READ first-updater-wins, SERIALIZABLE write skew, FOR UPDATE / NOWAIT / SKIP LOCKED, deadlock detection, concurrent unique inserts). Half: deterministic commit-window crash points: a static supervisor counts the server's mutating filesystem syscalls and SIGKILLs everything at the Nth, enumerated over six windows (up to 20 points each); after recovery the state must be exactly before or after (or a prefix).
scale0.10pgbench -i -s 10 (1M accounts) within 10 min; SIGKILL and restart to a correct count(*), sum(abalance) (full credit ≤10 s, none ≥30 s); -S throughput (full at 500 tps); TPC-B with 8 clients (full at 100 tps, invariant holds); restart again after writes. PostgreSQL itself: init 1.6 s, restart 4.8 s, pgbench -S 330,761 tps, TPC-B 604 tps.

Why these weights. SQL breadth is the largest single share because it is where real engineering effort goes and the regression suite gives a smooth, hard-to-saturate gradient. ACID is next because it is the point of the storage rule: keeping data in names and timestamps is easy; keeping it atomic and durable across a kill at any syscall is not. Protocol and clients together (0.35) reward being a server real drivers can use, and are deliberately not enough on their own: a v1-style toy that speaks the simple protocol and a tiny SQL subset gets a little of each and very little of the rest. Scale is small but forces recovery proportional to state, which rules out v1 Haiku's design (replay a log of every statement at start).

Storage rule and sandbox

The data directory is a 4 KB tmpfs (4M inodes) kept mounted by a holder container across kills; the server runs read-only with seccomp blocking setxattr, symlink, mknod/mkfifo, fallocate, io_uring and non-zero truncate; a scanner checks the directory every few seconds and any non-empty file, allocated block, xattr, symlink or special file zeroes the reward. PostgreSQL is calibrated with the storage check off, since it of course stores file contents. No full reference implementation was written: v1 already showed the rule is satisfiable (its toy and Haiku's server both passed it), and the grader's answers come from real PostgreSQL.

Exclusions

Regression files not run:

  • tablespace: creates directories on the server's filesystem
  • create_function_c: C-language functions loaded from regress.so
  • collate.icu.utf8: needs an ICU UTF-8 database; skips itself under C locale
  • collate.linux.utf8: needs a glibc UTF-8 locale database; skips itself under C locale
  • collate.windows.win1252: Windows-only
  • euc_kr: needs an EUC_KR database
  • opr_sanity: consistency checks of PostgreSQL's own catalog contents (zero rows expected; trivially matched by an empty catalog)
  • type_sanity: same as opr_sanity
  • misc_sanity: same as opr_sanity
  • oidjoins: same as opr_sanity

Statements not scored inside the files that run:

  • EXPLAIN plan text: 1,721 units
  • C function from regress.so: 37 units
  • server filesystem: 28 units
  • verbosity setting: 23 units
  • server filesystem path: 1 units

Server-side COPY t FROM 'file' is sent as psql \copy. Each statement has 20 s; after 3 timeouts in a row the rest of that file scores 0 and grading moves to the next file (PostgreSQL never times out, so this only shortens grading of servers that hang). A server that dies is restarted on the same data and the file continues in a new session.

Caveats

  • One 20-minute run per model is a sanity check, not a measurement.
  • Everything in the table was graded under the current rules (3-timeout SQL abort, crash points need an acknowledged control commit); PostgreSQL's ACID was rerun after the crash-point fix.
  • Throughput limits (500 / 100 tps) and restart limits were set from what PostgreSQL does in the same sandbox, not from an empty-files reference, so they may be generous or harsh for a metadata-only design.
  • The public kit is the grader's own harness code, with a 25/68 protocol subset, 34 of 214 regression files, and other ACID seeds; crash points are not public.

Next steps

  • Jack's call: a sweep (Opus, Sonnet, Haiku, Sol, Terra, Gemini) at 60 minutes, more than one rep each. Only the two 20-minute smoke runs (Haiku, Opus) have been run.
  • Both models stopped working early and answered resume nudges with "holding". A stronger keep-going nudge, or a rule that the session must end with a public-check run, would make longer runs measure ability rather than stopping behaviour.
  • The crash-point bug (a server that cannot run a window passed it) was caught by the v1-haiku baseline and fixed; worth auditing the other ACID scenarios for the same pattern of a vacuous pass.
  • Scale limits are set from PostgreSQL in the same sandbox; once a model gets pgbench -s 10 to load, check they are reachable by a metadata-only design.
