Find every duplicate file, as fast as you can

DRAFT, not published.

Six coding agents each had 15 minutes, six times over, to write the fastest correct duplicate-file finder, graded on 23 hidden test trees full of traps. Opus 5.5 was fastest on average, at 4.0× a naive baseline, then Sonnet 5.5 at 3.7×. Gemini 4 Argon's finished programs were as fast as Opus's, but one of its six runs ended with no program at all. Haiku 5.5 was slowest at 2.1×. The traps caught only two finished programs, both from GPT-6.1 Sol, which timed out on a 3 GiB sparse file.

"Find the duplicate files" sounds like an interview question, which makes it a good speed task: the answer is easy to check, the obvious solution is slow, and the fast solutions are full of ways to be subtly wrong. The traps are the point. A finder that trusts file sizes, a weak checksum, inode numbers or symlinks will be fast and wrong, and a wrong answer on any one tree costs more than speed can win back.

The prompt

Each agent ran headless in its own sandbox with one instruction, Read PROMPT.md in the current directory and do what it says. This is that file, word for word (with its hard line breaks joined), the same for every model:

# Write the fastest correct duplicate-file finder

Write a program that finds every set of files with identical contents under a directory tree. It is graded on hidden test trees, first for being exactly right, then for speed.

You have about 15 minutes. Work autonomously; nobody will answer questions. Keep making it faster (and keep it correct) until time runs out.

## What to deliver

- `/work/run.sh`: run as `sh /work/run.sh ROOT` with `/work` as the working directory. It prints the answer on stdout and exits 0.
- `/work/build.sh` (optional): run once, offline, before grading, with `/work` writable. Compile here. During grading, `/work` is **read-only** and `/tmp` is a fresh 1 GB tmpfs.
- Use anything in this image: Python 3.12 (standard library only), C/C++ (gcc), Rust (rustc and cargo, no crates), Go. There is no network.

## The exact rules

1. Walk every directory under ROOT that you can reach **without following symbolic links**.
2. A **candidate** is a regular file (by `lstat`) with size > 0 that you can open and read. Everything else is ignored, and is never an error: symlinks (never followed, whether they point to files, directories, devices, themselves or nowhere), FIFOs, sockets, device files, empty files, entries you can't `lstat`, files you can't open, and directories you can't open or list (and all that is inside).
3. Two candidates are **duplicates** when their contents are byte-for-byte identical.
4. **Hard links:** paths sharing an inode (same `st_dev` and `st_ino`) are one file, not duplicates of each other. A **group** is a set of two or more *distinct inodes* with identical contents. Print every reachable path of every inode in the group. An inode with several names and no identical twin is not a group.
5. **Names are bytes.** A name can hold any byte except `/` and NUL: newlines, invalid UTF-8, leading dashes, glob characters. Paths can be far longer than `PATH_MAX` and thousands of directories deep.
6. **Output:** each path relative to ROOT (no leading `./` or `/`, byte-exact), followed by a NUL byte; after the last path of a group, one more NUL byte. Example: `a/x\0b/y\0\0c\0d\0e\0\0`. The order of groups, and of paths within a group, doesn't matter. Nothing else on stdout. No groups: print nothing.

The tree is on tmpfs, mounted read-only, and nothing changes it while you run. Other filesystems and bind mounts can be mounted inside it; walk into them like any other directory. You run as the owner of the files with no capabilities, so permission bits apply to you.

## How it is graded

The hidden grader generates about 20 trees, runs your `run.sh` on each in a sandbox with **8 CPUs** and **8 GB** of memory, and measures wall-clock time from start to exit.

- A case is **correct** only if your groups are exactly the expected groups. Wrong, malformed, a non-zero exit, or slower than 10× the baseline plus 20 s, and the case fails.
- The **baseline** is a single-threaded Python program that walks the tree correctly and SHA-256 hashes every candidate in full. It scores 1.0 on every case.
- Each speed case scores `speedup = baseline_time / your_time`. A few small cases test correctness only and score 1.0 if right. A failed case scores 0.01, which is the same as being 100× slower than the baseline.
- **Reward = the geometric mean of the case scores.** One failed case costs far more than any single case's speed can win back.

The hidden trees are the same kinds of thing as the public ones, bigger, plus others that test the rules above. Expect: many GB of data; hundreds of thousands of files; one directory with 150k entries; chains thousands of levels deep; files that are all the same size and differ only in their first, last or a middle byte; large files that really are identical; sparse files with large apparent sizes; collisions for weak checksums; symlink loops; FIFOs; unreadable files and directories; and other filesystems and bind mounts inside the tree.

## Tools

- `python3 tools/check.py [name-filter] [-v] [--regen]` generates the public cases (small versions) under `/tmp/dupfind-public`, runs your `run.sh` on each, and checks the answer with the grader's rule.
- `tools/cases_public.py` is the generator for the public cases. `public/expected/` holds their answers.

Keep `run.sh` correct at all times. A failed case costs more than any speedup is worth.

So the agent knows the exact rules, how speed is scored, and the kinds of traps to expect. It gets the 7 public cases at 1/20 scale and a checker. It does not get the 16 hidden-only cases or their generators.

The traps

The grader builds 23 trees on a RAM disk at full scale and runs each solution on each one in a container with 8 CPUs, 8 GB of memory and no network. Fourteen cases are scored on speed, and nine are pass/fail:

  • Size doesn't help. Twenty 400 MB files identical except for the last byte. Others differ only in the first byte, or in one byte in the middle with matching heads and tails.
  • Weak checksums collide. Same size, same first and last 64 KiB, same CRC32, different bytes in the middle.
  • Every byte must be read. Large files that really are identical, and a 3 GiB sparse file whose holes make it a duplicate of a dense file full of zeros.
  • Hard links are one file. 8,000 inodes with 68,000 names between them. Names of one inode are not duplicates of each other.
  • Nothing may be followed. Symlink loops, links to ancestors, dangling links, FIFOs that block forever if opened, sockets and device links.
  • Paths are bytes and can be enormous. Newlines and invalid UTF-8 in names, and a chain 2,500 directories deep, far past PATH_MAX.
  • Scale. 300,000 files of 1 to 64 bytes, one directory with 150,000 entries, and 50,000 copies of one file.
  • Other filesystems inside the tree (new in this version). In cross_device, two tmpfs mounts whose inode numbers collide, so keying files on inode number alone merges different files. In bind_alias, a directory bind-mounted in two more places, so one file is reachable by several paths and every path must be printed.

The reward is the geometric mean over cases of the baseline's time divided by the solution's time. A pass/fail case scores 1 if right. Any wrong case scores 0.01. The baseline is a single-threaded Python program that walks the tree correctly and SHA-256 hashes every candidate in full.

How the 15 minutes went

The chart shows two ways of spending 15 minutes. The Claude models had a working finder about 2 to 4 minutes in, and every Sonnet and Haiku run had its final score within 7 minutes. Opus kept improving a little longer, its last change at 4:30 to 7:20. Then they stopped. Claude Code ends its session after each reply, so the harness resumed it with "You have about N minutes left. Keep working on the task in PROMPT.md." Opus, Sonnet and Haiku were resumed about 150 to 400 times per run, almost always to say the finder was final.

Sol and Terra climbed steadily for the whole run, in one or two long sessions, with 11 to 20 saved changes each. Gemini read and planned for 6 to 14 minutes without writing anything, then produced a finished, fast program in one go. Its first working copy already scored 3.8 to 4.6, and it barely changed after that.

One curve goes the wrong way. Sol's third run reached 3.62 at 10:50, its best score. A change after that made the final version time out on the 3 GiB sparse file, and it finished at 2.67. Sol's first run timed out on that case from its first graded copy to its last.

What the models did

Everyone wrote native code. On the first version of this benchmark, Haiku wrote Python and scored 0.99. This time all 35 finished runs were C or C++, compiled once in build.sh. All of them key files on inode, so hard links count once, and compare sizes before contents. Most read a few bytes from each file before committing to a full read, and most ask where a sparse file's data is (SEEK_DATA) instead of reading gigabytes of holes.

Gemini walks fastest and reads big files slowest. Gemini wrote the largest programs, 36 to 57 KB of C++ for the five that finished, each with a parallel directory walk on raw getdents64. That made it the fastest on tree-shaped cases: a median 63× on flat_sizes and 9.4× on hardlinks. But four of its five finished programs confirm matches with full SHA-256, so on 400 MB files that differ in one byte it managed a median 11× to 15×, where Opus reached 35× to 66×.

Sol and Terra wrote single-threaded programs. Both OpenAI models wrote short, careful C++ with plain opendir/readdir and a byte-for-byte compare. They tested hard: in one run Terra ran 100 randomized differential tests and reran its finder with only 8 to 11 open file descriptors. On a machine with 8 CPUs, one thread caps them on every read-heavy case. Terra was the most consistent model, all six runs between 2.63 and 2.91.

Opus has the widest spread. Its six runs range from 2.42 to 5.26. In one run of the first sweep it spent all 15 minutes trying to handle groups of same-size files too large to open at once. With the open-file limit forced to 100, its new fallback hung on 3,000 identical files, so it put back the previous version and stopped at 3.15. Two runs of the second sweep were slow on the last-byte case, 1.6× and 4.1×, against 50× for its best.

Gemini's failed run never got to a program. In the first sweep it spent 15 minutes designing and editing a 58 KB C++ file, never compiled it, and never wrote run.sh, so the grader had nothing to run. Its other five runs averaged 3.91, about the same as Opus's 4.01.

Did the traps work?

In these 36 runs the traps caught two programs, both Sol's, both on the sparse file. To check that they catch more than that, I ran a deliberately sloppy Python finder that groups files by size and their first 64 KiB. It gets 13 of 23 right and fails last_byte, hardlinks, symlinks, middle_byte, deep_pathmax, sparse_giant, crc_bait, trivial, cross_device, bind_alias.

The more useful test is the first version of this benchmark. It had 21 cases, without the two mount traps, and every model got all 21 right, so the traps separated nobody. I added cross_device and bind_alias, said in the prompt that mounts can appear inside the tree, and graded the six solutions from that first run on all 23 cases:

Caveats

  • Six runs per model. The spread within a model is up to 2.8 points (Opus 2.42 to 5.26), larger than most gaps between models. The two sweeps ranked the models differently: Gemini was fifth in the first, because of its empty run, and first in the second, ahead of Opus and Sonnet.
  • Hashes the grader can't catch. Several finished programs trust a home-made 128-bit hash and never compare the bytes: in the first sweep alone, Opus's third run, Sonnet's second and third, and Haiku's second. No fixed test tree can catch that, because it would need a collision built for each program's hash. The CRC32 trap only catches CRC32. Their answers were all right, but "correct on 23 trees" is not "correct".
  • Different harnesses. The Claude models ran in headless Claude Code, Sol and Terra in the Codex CLI, and Argon in the Gemini CLI in yolo mode. The Gemini CLI's own policy refused a few shell commands in some of Argon's runs, such as nm -D … | grep.
  • A leftover file in the first sweep. The previous version of the prompt (PROMPT.md.v1) was copied into every agent's folder by mistake. It is the same task without the line about mounts inside the tree, so it gives nothing hidden away. Gemini opened it in all three runs, and Haiku compared it with the real prompt once. The second sweep did not have it.
  • Sparse curves. Only 2 to 6 states per run were graded, so the curves show when the reward changed but not every step in between.
  • The reward is relative. On tiny trees the baseline's Python start-up dominates, so a large speedup there means less than it looks.

The prompt, grader, reference finders and harness are in dupfind-env/.
