Black-box database: rebuild a server you can only probe

Memorising PostgreSQL is worth almost nothing here: stock PostgreSQL scores 0.033 (it scored 1.0 on pgwire-db-env, and Opus's from-memory server 0.429), a perfect server for another seed scores 0.033, and a replay cache of everything a prober could record scores 0.058, while the oracle itself scores 1.000. The one model run, Opus 5.5 for 20 minutes, scored 0.066: it decoded the framing within 6 minutes but never logged in, because version 1 of this benchmark renamed the login keys with no way to discover them. That was a benchmark bug, not a capability result; oracle v2 fixes it with error hints, and no model has run on v2 yet.

The task

The model gets a TCP address (oracle:7000), two logins and a database name, and nothing else: no spec, no docs, no client library, no internet. It must work out the protocol and SQL behaviour by experiment and build a server, from scratch, that answers byte for byte the same and survives SIGKILL. The oracle is PostgreSQL 16.16 behind a seeded translating proxy, so every reference answer is free and exact. The prompt deliberately does not say the server is derived from a well-known open-source database: recognising it is part of the task, and saying so would hand over the prior that the perturbations exist to devalue. Full prompt: PROMPT.md.

Reading the ladder. The three ablation rows are the oracle with layers switched off, standing in for a model that reverse-engineered some layers perfectly and recalled the rest from PostgreSQL. Getting only the wire format right is worth 0.264: every SQL request in the variant's dialect is then a syntax error, and the durability checks cannot even run their queries. Wire plus the renamed words, with PostgreSQL's own error codes and value formatting, reaches 0.744; the semantics layer alone takes the last quarter. So each layer has to be learned by probing, and none can be skipped.

The replay cheat, before and after. The first version of the workloads logged in with byte-identical startup packets, so the cheat replayed its way past login and scored 0.69 on protocol (0.173 overall). Every login now carries a random application name, as real clients send, and the cheat falls to the replayed greeting plus connections it happens to close when the oracle does. Its SQL score was 0 both times: no request after login repeats across workload seeds.

The 0.13 protocol floor. Stock PostgreSQL, the other-seed servers and the cheat all collect about 0.13 on protocol, from workloads where the oracle simply closes the connection (bad magic, unknown user, malformed messages) and the candidate closes too. It is small and identical for every non-speaker, so it was left in rather than special-cased.

How it probed

It started with a raw socket, read the greeting, and decoded it within a few tool calls: type byte, then a length, then the banner "Obsidian 8.7" with a 2-byte length prefix, then a 4-byte magic. It then sent PostgreSQL-shaped startup packets (big-endian u32 length, user\0guest\0 C strings) and read the errors back. From "invalid startup packet layout: expected terminator as last byte" it worked out u16-prefixed strings and the two-zero-byte terminator; from "invalid length of startup packet" on lengths of 128 to 255 it found the varint length. It mapped the error fields (code, two severity copies, message) and wrote server.py reproducing the greeting and five login errors byte for byte.

Did it recognise PostgreSQL? Yes. Its very first login packets were PostgreSQL's layout, and by minute 7 it said so outright, noting that "the error codes look like PostgreSQL codes put through a per-code substitution table", and it guessed that the startup keys were disguised the same way. That was correct, and it was also the end of the road. The v1 oracle answered every key with "unrecognized configuration parameter" and never said what it wanted. Opus tried about 80 plausible names, single letters, rot13 and letter shifts, then brute-forced every 1 to 3 character lowercase key (about 20,000 logins). The real key, zenus, has 5 letters.

What this shows. The memorised prior helped and did not suffice. Knowing it was PostgreSQL told Opus what to look for (startup keys, terminator, SQLSTATE), but every byte still had to be found by experiment, and one undiscoverable byte string stopped everything behind it. That is the benchmark's fault, fixed in v2: the same probe now gets HINT: startup parameters are "zenus" (user name), "nutam" (database) and "sobi" (application name). Renamed SQL words had the same flaw; v2 adds hints for those too (below).

Wire layer: fresh type byte for every message in each direction; length as big- or little-endian u32 (counting itself or not) or a varint, before or after the type byte; integers big- or little-endian; strings NUL-terminated or u16-prefixed; the server speaks first with a greeting carrying the protocol magic; startup keys renamed; seeded codes for auth-ok, password request, cancel and encryption requests; 7 to 10 of PostgreSQL's 14 startup ParameterStatus kept, renamed; column descriptions lose table OID and attribute number, keep five fields in a seeded order; type OIDs remapped; error/notice field codes remapped and emitted in a seeded order (source file/line/routine dropped); ReadyForQuery status bytes and Describe/Close sub-types remapped. Dialect layer: 60% of 60 common keywords, 4 of 8 type families (all aliases), half of 18 functions plus pg_sleep get invented names; the old spellings become ordinary identifiers (so SELECT 1 is a syntax error); parameter marker $, ? or :; error positions mapped back to the client's text; PostgreSQL's spellings in tags, messages and default column names translated back. Semantics layer: SQLSTATE classes permuted; severity words renamed; booleans, integers (plain, +5, 1_000), floats (shortest, %.6g, %.3f, %.4e) and numerics (trailing zeros trimmed or not) reformatted; DateStyle set at login; INSERT tags without the OID or count-first; column names upper-cased or not; product name and version. Nothing needs a new engine: the proxy only rewrites what PostgreSQL computes.

What is graded

Grading never touches the oracle the model saw. A hidden workload seed generates fresh tables, values and statement mixes; the workloads are rendered into the variant's bytes, played against a fresh oracle (transcripts cached per seed) and against the candidate, and every reply message is compared byte for byte: 1 for identical, up to 0.5 for the right message type with some fields right, 0 otherwise; replies are aligned by message type within each step, and a step's denominator is the larger message count (plus one for a connection the oracle closes). BackendKeyData is compared by shape only.

Pass = the state equals the oracle's after replaying the acknowledged commits plus some subset of the in-flight ones (verify queries cast to text, so only lost, torn or phantom writes fail).

Why these weights. SQL behaviour is most of what "behaves identically" means and gives the smoothest gradient, so it gets the largest share. Durability is 0.30 because the brief makes persistence and crash safety first-class, and because it cannot be faked by replay. Protocol is 0.25: the handshake and framing are the first wall a model hits, and the extended flow and error paths are where a reverse-engineer who stops at "simple query works" leaves points. Every component is gated on the reverse-engineered protocol: a server that cannot log in earns nothing anywhere, which is what makes memorising PostgreSQL worthless.

Sandbox

Per run, a private internal Docker network holds three containers: the agent (Python 3.12 without sqlite3, gcc, Rust, Go, nc, hexdump, strace; no PostgreSQL client, library or documentation), one oracle (alias oracle), and an egress proxy that allows CONNECT to api.anthropic.com only (checked: PyPI is refused). The oracle's PostgreSQL roles are non-superusers and the proxy's code and seed are unreadable by the database user, so SQL cannot read the variant spec off disk. Grading runs the candidate read-only with 4 CPUs and 6 GB, data in a Docker volume that survives SIGKILL.

Caveats

  • The Opus number measures v1's bug, not the task. With the login key undiscoverable, no model could have passed login in v1 without guessing a 4 to 6 letter invented word. v2 is solvable in principle (every renamed item now has a discovery path), but nobody has shown it is solvable in 20 minutes. A model run on v2 is needed before the benchmark measures anything, and that run is Jack's call.
  • v2's hints are a design choice with a cost. They reveal a renamed word only when the client uses the PostgreSQL (or standard SQL) spelling, so knowing SQL is the key to discovering the dialect. That is deliberate (a model must still find every renaming by trying), but it means the dialect is learnable word by word rather than hidden.
  • Only the extended flow and simple queries are graded. COPY, binary formats, LISTEN/NOTIFY and function calls pass through the proxy with framing changes only and are not in any workload.
  • Public repo. The proxy, the generator and the default hidden workload seed (90210) are pushed to a public branch. Fine for a draft, but any real evaluation should rotate the variant seed and the workload seed, since both are trivially readable.
  • Message credit is generous to wrong-but-shaped replies (up to 0.5 for the right type with some fields right) and every non-speaker gets about 0.13 on protocol from matching connection closes. Both are small and identical across baselines.
  • Error positions are mapped back through the rewrite for errors that carry one; positions in errors raised while executing a named statement use that statement's map. Not checked against every PostgreSQL error path.
  • Durability runs the oracle's answer for every subset of in-flight commits (up to 16 with 4 writers). One in-flight operation per connection is the most the harness creates.
